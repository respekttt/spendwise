## Обсяг: лише помилки, відповідність checklist і CI

Бізнес-логіку (витрати, категорії, ліміти, звіти) **не реалізуй**. Схему БД не змінюй. Нових залежностей не додавай; якщо без цього ніяк — зупинись і поясни.

### 1. Формат помилок (`server/app.js`)

Поточний стан, який я бачу (перевір сам, а не вір на слово):

- невалідний JSON потрапляє в загальну гілку `4xx` і отримує `"Некоректний запит"`, а контракт для нього передбачає `"Невалідні дані запиту"`, як для помилок схеми;
- будь-яка інша `4xx` (зокрема `404`, `413`, `415`) отримує той самий `"Некоректний запит"`: код зберігається, але текст не описує проблему;
- у маршрутів немає способу повернути `400` з описом конкретного поля (`"amount: сума має бути більшою за 0"`) або `404` для неіснуючого `:id`. Бізнес-маршрутам це знадобиться наступним завданням;
- тести не перевіряють `Content-Type: application/json`, відсутність інших полів у тілі, `413`/`415` і `:id` на кшталт `0`, `-1`, `1.5`.

Що потрібно:

- **Одне місце формування тіла:** `setErrorHandler` і `setNotFoundHandler` дають рівно `{ "error": "<рядок українською>" }`, `Content-Type: application/json`. Жодних `statusCode`, `code`, `message` чи стеку.
- **Помилки застосунку:** простий механізм, через який маршрут кидає помилку з кодом (`400`/`404`) і **публічним** українським текстом, а обробник віддає цей текст як є (наприклад, клас `HttpError` в окремому модулі; де саме його покласти, щоб не порушити поділ із DoD, розділ 1, — вирішуй сам і поясни у звіті). Повідомлення будь-яких інших помилок, зокрема англійські тексти Fastify, у відповідь не потрапляють.
- **Помилки Fastify:** помилка схеми `params` → `404`; інші помилки схеми й невалідний JSON → `400` `"Невалідні дані запиту"`; інші `4xx` (`413`, `415` тощо) → їхній код і зрозумілий український текст для цього коду, із загальним запасним текстом для решти.
- **`500`:** усе інше, зокрема помилки без `statusCode` або з кодом `>= 500`, дає тіло `{ "error": "Внутрішня помилка сервера" }`, а оригінал іде в `request.log.error`. Подумай, як поводитися з помилкою, у якої `statusCode < 400`.
- Тексти помилок тримай в одному місці, а не розкидай рядками по коду.

### 2. Тести помилок (`tests/app.test.js` або окремий файл)

Тести перевіряють код, `Content-Type` і те, що тіло — об'єкт рівно з одним ключем `error` з непорожнім рядком. Точний текст перевіряй лише для `500`, бо його фіксує контракт. Мінімум:

- невідомий маршрут → `404`;
- `:id` = `abc`, `0`, `-1`, `1.5` у маршруті зі схемою `params` → `404`;
- помилка схеми тіла → `400`; невалідний JSON → `400`;
- непідтримуваний `Content-Type` → `415`; тіло понад `bodyLimit` → `413` (ліміт можна зменшити для тестового інстансу);
- помилка застосунку з кодом `400` і текстом поля → `400` з **цим** текстом; помилка застосунку з кодом `404` → `404`;
- неочікуваний виняток із текстом, схожим на SQL чи шлях до файла, → `500`, тіло точно `{ "error": "Внутрішня помилка сервера" }`, у тілі немає тексту винятку;
- `500` логується: перевір через логер, переданий у фабрику, без читання stdout.

Тимчасові маршрути для тестів реєструй лише в тестах, як зараз (`/__test/...`); у робочому застосунку їх не має бути.

### 3. Відповідність `standards/checklist.md`

Пройди checklist рядок за рядком: матрицю, скрипти `package.json`, `.gitignore`, hook, `biome.json` (`*.md` виключено саме так, як там написано), тести зі списку сценаріїв, що вже стосуються фундаменту (smoke, ініціалізація, версія). Що розходиться з кодом — виправ; що розходиться і не виправляється без зміни документа — опиши у звіті. Окремо перевір кінці рядків: у мене Windows і `core.autocrlf=true`, а CI буде на Linux. Подивись `git ls-files --eol`, чи `bun run check` пройде на чистому checkout. Якщо для цього треба розширити `.gitattributes`, поясни навіщо.

### 4. CI — `.github/workflows/ci.yml`

Точно за рядком «CI» з checklist:

- тригери: `push` і `pull_request`;
- `runs-on: ubuntu-latest`, `permissions: contents: read`;
- кроки: checkout → встановлення Bun → `bun install --frozen-lockfile` → `GIT_SHA` з `git rev-parse --short HEAD` у `$GITHUB_ENV` → `bun run ci`;
- версії actions закріплені (щонайменше мажорна версія). Bun у CI має відповідати `engines` з `package.json`: перевір у документації `oven-sh/setup-bun`, як задати версію (явно чи з файла), і вибери одне джерело правди. Пояснення — у звіті;
- без кешів, матриць і додаткових job-ів, поки вони не потрібні.

Подумай про `pull_request`: `actions/checkout` там бере merge-коміт, тож `git rev-parse --short HEAD` дасть не SHA останнього коміту гілки. Нічого не вигадуй: опиши це у звіті як відкрите питання з варіантами, а в workflow зроби точно як у checklist.

YAML не перевіряється Biome. Перевір його синтаксис будь-яким доступним способом без нових залежностей у проєкті (або скажи, що не зміг).

## Як працювати

- Невеликими кроками; після кожного логічного кроку — `bun run ci`.
- Не комітить і не пуш сам: я переглядаю diff, комічу й пушу. Через це зелений job в Actions ти побачити не можеш, тож не пиши, що CI пройшов. Пиши, що `bun run ci` пройшов локально, і що я маю перевірити після push.
- Не вимикай правила Biome і не пропускай тести, щоб «стало зелено». Якщо щось не виходить — зупинись і опиши.

## Самоперевірка і звіт

Наприкінці прожени `bun run ci` і встав у звіт **повний вивід** разом з кодом виходу. Потім звіт у такому форматі:

1. **Що зроблено** — список файлів, по одному реченню про кожен.
2. **Контракт, «Загальні правила»** — таблиця по кожному пункту (`400`, `404`, тіло помилки, `500`, інші `4xx`): виконано (який тест це доводить) / частково / N/A з причиною. Пункт «дані не змінюються, транзакції» — N/A, поки немає маршрутів, що пишуть у БД.
3. **Checklist** — рядки матриці: відповідає / виправлено / розходиться (чому).
4. **DoD, розділ 3** — виконано / не виконано / N/A з причиною. Пункт «CI пройшов» — «не перевірено: потрібен push».
5. **Відхилення від документів** і чому.
6. **Відкриті питання та ризики**: SHA на `pull_request`, кінці рядків і все суперечливе, що знайдеш у контракті чи checklist.
7. **Що перевірити мені після push** — коротким списком.
