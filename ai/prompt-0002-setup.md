## Роль і джерела істини

Ти працюєш у репозиторії Expense Tracker. Пиши код **лише** за цими документами; якщо вони суперечать один одному або чогось бракує — зупинись і спитай, не вигадуй:

1. `spec.md` — межі, правила, критерії прийняття (далі «AC»).
2. `specs/api-contract.md` — маршрути, формати, коди відповідей, тіло помилки.
3. `server/db/schema.sql` — схема БД, **не змінюй** її в цьому завданні.
4. `standards/` — `definition-of-done.md`, `checklist.md` (скрипти, hook, `.gitignore`, сценарії тестів), `spec-format.md`, `adr/001`–`003`.

Спершу прочитай усі ці файли повністю. Документи в `spec.md`, `specs/`, `standards/`, `ai/` не редагуй; якщо вважаєш, що там помилка, — опиши її у звіті.

## Обсяг цього завдання: лише фундамент

Бізнес-логіку (витрати, категорії, ліміти, звіти) у цьому завданні **не реалізуй** — вона буде окремими завданнями з власними тестами. Зараз потрібен каркас, на який вона ляже, і робоча система перевірок.

### 1. Інструменти та залежності

- Bun (зафіксуй мінімальну версію в `package.json` → `engines` і в README).
- Fastify — у `dependencies` з точною версією.
- Biome — `bun add -d --exact @biomejs/biome`; `biome.json` з форматуванням і лінтером для JS/JSON/CSS. Перевір `bunx biome check --help`, що закріплена версія підтримує `--staged`; якщо ні — скажи у звіті й запропонуй заміну.
- Без інших залежностей без потреби; якщо додаєш — поясни навіщо.

### 2. `package.json` — скрипти

Точно як у `standards/checklist.md`: `check`, `check:staged`, `test`, `smoke`, `build`, `ci` (`bun run check && bun test && bun run build`).

### 3. Git

- `.gitignore` — шаблони з `standards/checklist.md`.
- `.githooks/pre-commit` — вміст з checklist (Biome staged → smoke → tests → build), `set -eu`, виконуваний (`git update-index --chmod=+x`, бо я на Windows).
- У README — команда `git config core.hooksPath .githooks`. Сам цю команду не виконуй і `--no-verify` не використовуй.

### 4. Структура і каркас сервера

```
server/
  main.js        — точка входу: читає PORT і шлях до БД з env, викликає createApp, слухає порт
  app.js         — фабрика createApp({ dbPath, now, version }) → Fastify-інстанс
  db/schema.sql  — вже існує
  db/index.js    — openDb(path): відкриває bun:sqlite, PRAGMA foreign_keys = ON, виконує schema.sql
  core/time.js   — kyivToday(now) і addDays — як в ADR 003 (лише ці функції, без бізнес-правил)
  routes/        — поки лише version.js
public/          — index.html-заглушка, віддається як статика
tests/
  smoke.test.js
```

Вимоги до каркасу:

- **Годинник (ADR 003):** `createApp` приймає `now` (за замовчуванням `() => new Date()`); `server/core/` не викликає `new Date()` без аргументів.
- **БД:** `PRAGMA foreign_keys = ON` одразу після відкриття **кожного** з'єднання; ініціалізація через `schema.sql` (шлях відносно файла модуля, не `cwd`). Тести використовують `:memory:` або тимчасовий файл.
- **Помилки (контракт, «Загальні правила»):** `setErrorHandler` і `setNotFoundHandler` повертають `{ "error": "<опис українською>" }`; невідомий маршрут — `404`; помилка валідації схеми — `400`.
- **`GET /version`:** точно за контрактом — `text/plain`, `GIT_SHA` → інакше `git rev-parse --short HEAD` → інакше `unknown`, усе з кодом `200`. Значення визначається один раз під час старту; для тестів його можна передати через параметр `version` фабрики.
- `bun build server/main.js --target=bun --outdir=dist` має проходити.

### 5. Тести цього завдання

- `tests/smoke.test.js`: застосунок з `:memory:`, `GET /version` → `200`, `text/plain`, непорожнє тіло.
- Ініціалізація (AC 9): двічі виконати ініціалізацію на одному файлі БД → «Інше» одна; `PRAGMA foreign_keys` = `1` для кожного нового з'єднання.
- Версія (AC 8): з `GIT_SHA` → це значення; без `GIT_SHA` у репозиторії → збігається з `git rev-parse --short HEAD`; без обох джерел → `unknown`.
- `kyivToday`: `2026-07-15T21:30:00Z` → `2026-07-16`, `2026-01-15T21:30:00Z` → `2026-01-15`; `addDays` через межу місяця й переходу на літній час.
- Невідомий маршрут → `404` з тілом `{ error }`.

## Самоперевірка і звіт

Наприкінці прожени `bun run ci` і встав у звіт **повний вивід** (код виходу). Потім звіт у такому форматі:

1. **Що зроблено** — список файлів із одним реченням про кожен.
2. **AC зі `spec.md`** — таблиця по всіх 9: `виконано` (який тест це доводить) / `частково` / `N/A — не в обсязі 0003`. Очікувано виконані лише 8 і 9, решта — N/A; не видавай нереалізоване за готове.
3. **DoD** — пункти розділу 3 «Якість і перевірки» з `definition-of-done.md`: виконано / не виконано / N/A з причиною.
4. **Відхилення від документів** і чому.
5. **Відкриті питання та ризики** — зокрема все, що знайшов суперечливого в spec/контракті/checklist.
