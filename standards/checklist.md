# Checklist перевірок — Expense Tracker

## Матриця перевірок

| Перевірка | Чим виконується | Коли запускати | Критерій успіху |
|---|---|---|---|
| Стиль і статичний аналіз JS/JSON/CSS* | **Biome:** `bun run check` (весь проєкт), `bun run check:staged` (лише файли з індексу) | `check:staged` — у pre-commit; `check` — у CI | Код виходу `0`; немає помилок форматування або правил Biome. |
| Модульні тести бізнес-правил | **Bun:** `bun test` | Після змін `server/core/`, перед комітом, у CI | Усі наявні тести пройшли. |
| Інтеграційні тести HTTP/SQLite | **Bun test** з ізольованою тестовою БД (`:memory:` або тимчасовий файл) і фіксованим годинником | Після змін API, БД, транзакцій та в CI | Відповіді й статуси збігаються з `specs/api-contract.md`, інваріанти БД — з `server/db/schema.sql` і spec. |
| Smoke-тест | **Bun:** `bun run smoke` | У pre-commit (перший після Biome), у CI як частина `bun test` | Застосунок створюється з БД `:memory:`, `GET /version` → `200`, тіло непорожнє. |
| Збірка | **Bun:** `bun run build` | У pre-commit і CI | Код виходу `0`: усі модулі `server/` збираються, імпорти не зламані. `dist/` не комітиться. |
| Перевірки перед комітом | **Git pre-commit hook**: формат і лінтер (Biome), smoke-тест, тести, збірка | Під час `git commit` | Коміт блокується, якщо будь-який крок упав. |
| CI | **`bun run ci`** (Biome, усі тести, збірка) у чистому середовищі | На кожен push і PR; локально — та сама команда | Пайплайн зелений; без цього завдання не Done. |
| Перевірка UI | **Ручна перевірка в браузері** | Після змін `public/` | Форми, звіти, помилки й `warning` відображаються очікувано. |
| Узгодженість документації | **Ручне порівняння** зі spec, контрактом API, схемою БД, DoD, ADR | При зміні контрактів/правил | Документація не суперечить реалізації. |
| Відсутність приватних файлів | **Git:** `.gitignore` + `git status --short` і `git diff --cached --name-only` | Перед комітом | Немає файлів робочої БД, секретів або тимчасових артефактів. |

\* Biome перевіряє лише підтримувані типи файлів згідно з конфігурацією і версією. Markdown-специфікації перевіряються вручну; цей пункт не означає автоматичну перевірку `.md`.

## Налаштування `package.json`

Biome закріплюється в `devDependencies` з точною версією, щоб hook і CI не залежали від автоматичного завантаження пакета через `bunx`:

```bash
bun add -d --exact @biomejs/biome
```

```json
{
  "scripts": {
    "check": "biome check .",
    "check:staged": "biome check --staged --no-errors-on-unmatched",
    "test": "bun test",
    "smoke": "bun test ./tests/smoke.test.js",
    "build": "bun build server/main.js --target=bun --outdir=dist",
    "ci": "bun run check && bun test && bun run build"
  }
}
```

`--staged` обирає лише файли з індексу Git, тож незакомічені зміни в інших файлах не впливають на результат hook. Прапорець доступний не в усіх версіях Biome: перевірте `bunx biome check --help` для закріпленої версії. Якщо файл застейджено лише частково, Biome може бачити його робочу версію, а не ту, що потрапить у коміт; CI перевіряє весь проєкт і ловить такі випадки.

`server/main.js` — точка входу сервера. Збірка через `bun build` перевіряє, що весь граф імпортів `server/` розв'язується і модулі синтаксично коректні; `public/` віддається як статичні файли й не збирається. Результат у `dist/` не розгортається: сервер запускається з вихідних файлів, тож шляхи на кшталт `server/db/schema.sql` у збірці не перевіряються — це покриває smoke-тест.

`bun run ci` — одна команда для повної перевірки локально, у CI і під час демонстрації.

## Мінімальні локальні команди

```bash
# Встановлення залежностей (за наявного package.json)
bun install

# Перевірка форматування та якості коду
bun run check

# Запуск усіх тестів, що знаходить Bun
bun test

# Лише smoke-тест і збірка
bun run smoke
bun run build

# Повна перевірка (як у CI)
bun run ci

# Перевірка того, що потрапляє в коміт
git diff --cached --name-only

# Очікуване значення для GET /version
git rev-parse --short HEAD
```

> **Важливо:** ці команди є стандартом проєкту, а не звітом про вже налаштовані чи успішно виконані перевірки. Для Biome потрібні встановлений `@biomejs/biome` та відповідна конфігурація; для `bun test` — створені тести. Якщо інтеграційні тести розміщено окремо, їх теж потрібно додати до запуску, а не вважати автоматично охопленими.

## Сценарії, які тести мають охоплювати

Тести, що залежать від дати, створюють застосунок із фіксованим `now()` (ADR 003), а не покладаються на поточний час машини.

| Область | Мінімальна перевірка | Очікувано |
|---|---|---|
| Smoke | Створити застосунок з БД `:memory:`, `GET /version` | `200`, `text/plain`, непорожнє тіло. Файл — `tests/smoke.test.js`. |
| Гроші | Створити витрати `0.10` і `0.20` | Загальна сума `0.30` грн. |
| Гроші та ліміт | Категорія з лімітом `0.30`, витрати `0.10` і `0.20` | `warning` **немає**. |
| Округлення й валідація суми | `amount`: `0.004`, `0`, `-5`, `"12.5"`, відсутнє поле | HTTP `400` для кожного. |
| Дата | `2026-02-30`, `2026-2-3`, `03.02.2026`, завтра за `Europe/Kyiv` | HTTP `400`. |
| Межа доби | `now = 2026-07-15T21:30:00Z` (у Києві 00:30 16 липня), витрата з датою `2026-07-16`; `now = 2026-01-15T21:30:00Z` (у Києві 23:30 15 січня), витрата з датою `2026-01-16` | Перша → `201`, друга → `400`. |
| Ковзне вікно | Дати `T - 29`, `T - 30`, `T` | `T - 29` і `T` враховані в ліміті й 30-денному звіті; `T - 30` — ні, але входить у місячний звіт свого місяця. |
| Категорія «Інше» | Спроба видалити, перейменувати, додати ліміт або створити дублікат (`"інше"`, `" Інше "`) | HTTP `400`. |
| Кириличні дублікати | Є `"Їжа"`; створити або перейменувати іншу категорію на `"їжа"`, `"  ЇЖА "` | HTTP `400`. |
| Назва категорії | `""`, `"   "` | HTTP `400`. |
| Видалення категорії | Видалити категорію з витратами | Витрати перенесені в «Інше», загальна сума незмінна. |
| Атомарність видалення | Змусити `DELETE` впасти після `UPDATE` (наприклад, підмінити крок у тесті) | Транзакція відкочена; витрати лишилися в початковій категорії. |
| `ON DELETE RESTRICT` | Прямий `DELETE FROM categories` для категорії з витратами | SQLite відхиляє операцію. |
| Ліміти | Додати/змінити витрату або знизити ліміт понад поріг | Дані збережені (`200/201`), відповідь містить `warning` зі структурою з контракту API. |
| Зміна категорії витрати | Перенести витрату в категорію, де вона перевищує ліміт | `200`, `warning` для **нової** категорії. |
| Рівно на ліміті | Сума за 30 днів дорівнює ліміту | `warning` немає. |
| API | Неіснуючий `category_id` у тілі; неіснуючий або нечисловий `:id` в URL (`/expenses/999`, `/expenses/abc`) | Відповідно `400` та `404`. |
| Звіти | Порівняти місячний і 30-денний звіти | Місячний без полів лімітів; 30-денний зі станом лімітів. |
| Порожній період | Звіти без жодної витрати за період | `200`, `total = 0`, `categories = []`, без `NaN`. |
| Параметр місяця | `2026-13`, `2026-1`, майбутній місяць, відсутній `month` | HTTP `400`. |
| Ініціалізація | Створити порожню БД, двічі запустити ініціалізацію | «Інше» існує в одному екземплярі; `PRAGMA foreign_keys` повертає `1` для кожного нового з'єднання. |
| Версія | `GET /version` | `text/plain`, збігається з `git rev-parse --short HEAD`; без `.git` і `GIT_SHA` — `unknown`. |

## Приклад Git pre-commit hook

Це **приклад конфігурації**, а не твердження, що hook уже існує. Створіть у репозиторії `.githooks/pre-commit` із таким вмістом:

```sh
#!/bin/sh
set -eu

echo '[pre-commit] Format + lint (Biome, staged files)'
bun run check:staged

echo '[pre-commit] Smoke test'
bun run smoke

echo '[pre-commit] Tests'
bun test

echo '[pre-commit] Build'
bun run build
```

Smoke-тест також входить у `bun test`; окремий крок іде першим, щоб коміт зупинявся якнайшвидше, якщо застосунок узагалі не стартує.

Після додавання файла налаштуйте його використання:

```bash
# macOS/Linux або Git Bash на Windows
chmod +x .githooks/pre-commit

git config core.hooksPath .githooks
```

**Правило:** не обходити hook через `git commit --no-verify` без задокументованої причини. У CI слід запускати ті самі перевірки незалежно від локального hook, бо локальний Git hook не є гарантією виконання в чужому середовищі.
