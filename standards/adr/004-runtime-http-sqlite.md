# ADR 004: Рантайм, HTTP-фреймворк і драйвер SQLite — Bun + Fastify + `bun:sqlite`

- **Status:** Accepted
- **Date:** 2026-11-12
- **Related spec:** `spec.md`, розд. 2 «Архітектура та компоненти»

## Context

Spec у розд. 2 називає стек одним рядком (Bun + Fastify + `bun:sqlite`), але не пояснює вибору. Каркас завдання 1 уже на ньому побудований, а наступні завдання (CRUD, звіти) лише додаватимуть маршрути й запити. Тому аргументи треба записати зараз, поки рішення ще дешево переглянути.

Рантайм, фреймворк і драйвер БД обираються разом: від рантайму залежить, який драйвер SQLite працює без збирання нативного коду і який тест-раннер доступний.

Обмеження проєкту:

- Однокористувацький локальний інструмент без авторизації; одна SQLite-БД; навантаження мізерне.
- Розробка на Windows, CI — `ubuntu-latest`. `bun install` має давати однаковий результат в обох середовищах без компіляції.
- Контракт API вимагає власний формат помилок `400`/`404`/`500` українською і перевірку типів на сервері.
- Checklist вимагає інтеграційних тестів HTTP з БД `:memory:` і фіксованим годинником (ADR 003).

## Decision Drivers

- **Мінімум залежностей:** кожна залежність — точна версія, яку треба оновлювати й пояснювати.
- **Відтворюваність:** однакова поведінка на Windows і Linux, жодного нативного коду в `bun.lock`.
- **Валідація на сервері:** типи й формати вхідних даних перевіряються декларативно, а не вручну в кожному маршруті.
- **Тестованість:** HTTP-тести без відкриття порту, БД у пам'яті.

## Considered Options

### Рантайм і HTTP

1. **Node.js + Express:** найпоширеніший варіант. Але валідації за схемою немає (потрібна ще залежність), а тест-раннер, збірка й SQLite-драйвер — окремі пакети.
2. **Bun + `Bun.serve` без фреймворку:** нуль залежностей, але маршрутизацію, розбір і валідацію JSON, `404`, статику з захистом від `../` довелося б писати й тестувати самостійно.
3. **Bun + Hono:** легкий, створений під Bun-подібні рантайми. Валідація — через middleware й адаптери до бібліотек схем (ще залежність); тести — через `app.request()`. Рівноцінний варіант, але під вимоги контракту дає менше з коробки.
4. **Bun + Fastify:** валідація JSON Schema вбудована; `setErrorHandler`/`setNotFoundHandler` дозволяють привести всі помилки до формату контракту в одному місці; `app.inject()` для тестів без мережі; офіційний `@fastify/static`. Fastify орієнтований на Node і працює в Bun через сумісність з `node:http`.

### Драйвер SQLite

1. **`better-sqlite3`:** зрілий, синхронний, швидкий; саме його API наслідує `bun:sqlite`. Але це нативний аддон, зібраний під ABI Node: на Windows без готового бінарника потрібні Python і MSVC для `node-gyp`, а в Bun його робота залежить від шару сумісності з аддонами Node і мусить перевірятися на кожній версії рантайму. До того ж це ще одна залежність, причому з нативним кодом.
2. **`bun:sqlite`:** вбудований у рантайм, нічого не встановлюється і не компілюється; синхронний API (`prepare`, `run`, `transaction`), `strict: true` для іменованих параметрів без префікса. Мінус — працює лише під Bun.
3. **ORM / query builder (Drizzle, Knex):** абстракція над SQL і міграції. Для схеми з двох таблиць і кількох запитів — зайвий шар; інваріанти (`ON DELETE RESTRICT`, транзакція видалення категорії) зручніше бачити в чистому SQL.

## Decision

Обрано Bun + Fastify (варіант 4) і `bun:sqlite` без ORM (варіант 2).

- **Рантайм:** Bun, точна версія `1.4.4` у `package.json` → `packageManager` (її читає `setup-bun` у CI), мінімальна — `engines.bun`. Bun дає в одному бінарнику менеджер пакетів (`bun.lock`, `--frozen-lockfile`), тест-раннер (`bun test`), збірку (`bun build`) і SQLite.
- **HTTP:** Fastify (точна версія в `dependencies`), статика — `@fastify/static`. Застосунок створюється фабрикою `createApp({ dbPath, now, version, logger })` у `server/app.js`; тести працюють через `app.inject()`.
- **БД:** `bun:sqlite`; схема — `server/db/schema.sql`, `PRAGMA foreign_keys = ON` на кожне з'єднання (`server/db/index.js`). `better-sqlite3` відхилено через нативну збірку й залежність від сумісності Bun з аддонами Node, хоча за API вони майже однакові: перехід між ними, якщо знадобиться, зачепить лише `server/db/`.

## Consequences

### Позитивні
- Дві runtime-залежності з точними версіями (`fastify`, `@fastify/static`), жодного аддона, який треба компілювати: `bun install` однаковий на Windows і Linux.
- Валідація за схемою і єдиний обробник помилок дають формат контракту в одному місці (`server/errors.js`), а не в кожному маршруті.
- Маршрути тестуються інтеграційно через `inject()` з `:memory:` без відкриття порту.

### Негативні / компроміси
- **Прив'язка до Bun:** `bun:sqlite`, `bun:test`, `import.meta.main` не працюють у Node. Перехід на Node означає заміну драйвера БД і тест-раннера. Для навчального однокористувацького проєкту приймаємо.
- Fastify розрахований на Node; у Bun він працює через шар сумісності, тож оновлення Bun може зачепити його поведінку. Ловиться тестами в CI на точній версії Bun.
- Повідомлення Fastify англійською — їх доводиться перехоплювати й замінювати (`server/errors.js`); новий тип помилки фреймворку без тесту може просочитися як `500`.

### Подальші дії
- Під час оновлення Bun змінювати `packageManager` і `engines.bun` одним комітом і проганяти `bun run ci`.
- Для кожного нового маршруту описувати JSON Schema і тестувати помилки валідації на формат контракту.
