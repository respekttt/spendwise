# ADR 011: Рівні тестів, одна команда й мутаційне тестування StrykerJS через `command`-runner

- **Status:** Proposed
- **Date:** 2026-11-21
- **Related spec:** `specs/testing.md`, ВП-1…ВП-7, критерії 1–8
- **Related ADR:** 004, 005, 007, 008

## Context

`specs/testing.md` описує три рівні тестів, одну команду для всіх, мутаційне тестування з класифікацією вижилих мутантів і порядок «До → підсилення → Після». Сім питань spec залишила цьому ADR. Обмеження, у які впираються відповіді:

- **Покриття в Bun.** `bun test --coverage` рахує лише рядки й функції; гілок немає, а поріг `statements` Bun приймає, але не застосовує (документація Bun, «Code coverage»). Тест-раннер змінити не можна без переписування 349 тестів на `bun:test` (ADR 004).
- **StrykerJS і Bun.** Офіційних runner-ів у StrykerJS є кілька (Jest, Mocha, Jasmine, Karma, Vitest, Tap, Cucumber), але для `bun test` немає. Є два сторонні: `stryker-mutator-bun-runner` (0.4.0, з per-test покриттям) і `@hughescr/stryker-bun-runner`. Перший інший проєкт пробував і відмовився через несумісність з Bun 1.3.0; у другого описано проблеми з тайм-аутами. Вбудований `command`-runner запускає будь-яку команду: активного мутанта передає змінною оточення, мутанта вважає вбитим за ненульовим кодом виходу, покриття й окремих тестів не знає (вихідний код `command-test-runner.ts`). Тому з ним `coverageAnalysis` може бути лише `off`: кожен мутант запускає всю команду.
- **Час.** Увесь набір триває близько 7 с (`bun run ci`, 349 тестів, з них тести з дочірнім процесом і блокуванням БД — по кількасот мілісекунд). Unit-тести (`core.test.js`, `time.test.js`, 26 тестів) — частки секунди.
- **Обсяг мутацій.** Spec вимагає, щоб у розділі «До» знайшлося щонайменше три реальні прогалини (AC 7). `server/core/reports.js` уже частково покритий у `tests/core.test.js`, тож мутації на ньому одному можуть дати менше трьох чесних вижилих мутантів.
- **Windows без `make`.** Розробка на Windows, CI на Linux (ADR 005). `make` у Windows за замовчуванням немає, у `ubuntu-latest` він є.
- **Без Docker.** SQLite — файл, «міграція» — `schema.sql` на старті (ADR 004, ADR 008). «Підняти залежності» тут означає створити тимчасовий каталог з БД і запустити процес сервера.

Тут кілька розвилок в одному ADR, бо вони залежать одна від одної: від runner-а залежить, скільки триває прогін на мутанта; від цього — які тести запускати і який обсяг мутувати; від обсягу — поріг; від розкладки тестів — як запускати рівень і що мутаційний прогін вважає «unit».

## Decision Drivers

- **Відтворюваність:** одна команда для тестів і одна для мутацій, однаково на Windows і в CI.
- **Час мутаційного прогону:** хвилини, а не години, щоб «До» і «Після» можна було повторювати.
- **Чесний звіт:** обсяг, на якому вижилі мутанти справді показують слабкі тести, а не штучно виловлені.
- **Мінімум залежностей** (ADR 004): одна нова dev-залежність, лише для мутацій.
- **Перевірюваність меж рівнів**, як шарів в ADR 007.

## Considered Options

### Інструмент мутацій і runner (ВП-2)

1. **StrykerJS + `command`-runner (`bun test …`).** Офіційна частина `@stryker-mutator/core`, працює з будь-якою командою. Без покриття: кожен мутант запускає всю команду, тож вона мусить бути швидкою.
2. **StrykerJS + сторонній runner для Bun.** Per-test покриття зробило б прогін швидшим, але обидва пакети неофіційні, а щодо першого є задокументована несумісність з Bun 1.3.0; на Bun 1.4.4 їх ніхто не перевіряв.
3. **Інший інструмент** (mutmut, PIT, cosmic-ray). Вони для Python і Java; для JavaScript реальної альтернативи StrykerJS немає.
4. **Власний скрипт мутацій.** Повний контроль, але це пишеться заново те, що Stryker уже вміє: мутатори, звіти, тайм-аути.

### Які тести запускати на кожного мутанта (ВП-3)

1. **Увесь набір (`bun test`).** Найповніше: мутанта вб'є будь-який тест. Але з `coverageAnalysis: off` кожен мутант чекатиме ~7 с; на кількасот мутантів це десятки хвилин навіть паралельно, а тести з файлами БД і портами за паралельного запуску в кількох пісочницях можуть заважати один одному.
2. **Лише unit (`bun test ./tests/unit`).** Секунди на мутанта, без файлів і портів. Мутаційний score тоді вимірює саме unit-рівень `server/core/`: мутант, якого вбили б лише інтеграційні тести, у цьому прогоні виживе.

### Обсяг мутацій (ВП-3)

1. **Лише `server/core/reports.js`.** Найшвидше, але ризик, що чесних вижилих мутантів у «До» буде менше трьох.
2. **Увесь `server/core/`, крім `errors.js`.** 284 рядки чистих функцій: гроші, назви, час, валідація, відбиток ключа, звіти; `errors.js` — лише класи без логіки. Unit-тести вже існують для частини модулів, тож прогалини будуть, і справжні.
3. **`server/core/` і сервіси чи репозиторії.** Їх перевіряють лише інтеграційні тести, а вони за варіантом 2 попереднього пункту на мутантах не запускаються.

### Покриття гілок (ВП-1)

1. **Лише рядки й функції з `bun test --coverage`.** Рядок з `if` рахується покритим, навіть якщо гілку `else` ніхто не перевіряв.
2. **Перенести unit-тести під Node з c8/Istanbul.** Тести імпортують `bun:test`; два раннери й дві версії тих самих тестів.
3. **Ручний перелік гілок для `reports.js` + мутанти умов як сигнал для всього обсягу.** Перелік у `specs/testing.md`, розд. 3, зіставлено з кожною гілкою коду; мутатори `ConditionalExpression`, `EqualityOperator`, `LogicalOperator`, `BlockStatement` змінюють саме гілки, і вижилий мутант умови показує неперевірену гілку точніше, ніж відсоток рядків.

### Одна команда (ВП-5)

1. **`Makefile`.** Збігається з формулюванням завдання (`make test`), але в Windows `make` треба ставити окремо.
2. **Скрипти `package.json`.** Однаково працюють у Windows і CI, бо Bun уже є.
3. **Обидва:** скрипти як джерело істини і тонкий `Makefile`, де кожна ціль — один виклик `bun run …`.

### Розкладка тестів (ВП-6)

1. **Каталоги `tests/unit/`, `tests/integration/`, `tests/e2e/`.** Рівень видно з шляху; `bun test ./tests/unit` запускає рівень; тест імпортів перевіряє межі за каталогом.
2. **Суфікси назв (`*.unit.test.js`).** Рівень видно з назви, але фільтр за назвою в `bun test` — підрядок шляху, і помилка в суфіксі мовчки виводить файл з рівня.

### CI (ВП-7)

1. **Усе в CI**, зокрема мутації. CI довший на хвилини, і потрібен Node чи інше середовище для Stryker.
2. **Unit, інтеграційні й E2E у CI, мутації локально** зі звітом у git.

## Decision

Обрано: StrykerJS з `command`-runner-ом; на мутантах запускаються лише unit-тести; обсяг — увесь `server/core/`, крім `errors.js`; покриття гілок — ручний перелік для `reports.js` і мутанти умов; скрипти `package.json` і тонкий `Makefile`; каталоги за рівнями; у CI — усі три рівні, мутації — локально.

### Розкладка й рівні

- `tests/unit/` — лише імпорти з `server/core/` і `bun:test`; `tests/integration/` — будь-що з `server/`; `tests/e2e/` — нічого з `server/`, лише `node:*`, `bun:test` і HTTP до процесу. Спільні хелпери — `tests/helpers/`, з тим самим правилом за рівнем, що й тести, які їх імпортують.
- Наявні файли переїжджають: `core.test.js` і `time.test.js` → `unit/` (крім тесту, що сканує `server/core/` на `new Date()`: він читає файли, тож іде в `integration/`); `startup.test.js` → `e2e/`, а тести `defaultDbPath` з нього → `integration/` (spec, розд. 2); решта → `integration/`.
- Правила рівнів додаються в той самий тест, що сканує імпорти шарів (ADR 007, AC 16), і перевіряються самоперевіркою, як інші правила.

### Команди

| Скрипт `package.json` | Що робить |
|---|---|
| `test:unit` | `bun test ./tests/unit` |
| `test:integration` | `bun test ./tests/integration` |
| `test:e2e` | `bun test ./tests/e2e` |
| `test:all` | `test:unit`, потім `test:integration`, потім `test:e2e`; зупиняється на першому, що впав |
| `mutation` | `stryker run` з `stryker.config.json` |
| `ci` | `check`, `test:all`, `build` (замість `bun test`) |

- `Makefile` має дві цілі, `test` → `bun run test:all` і `mutation` → `bun run mutation`, і більше нічого. Скрипти — джерело істини; на Windows без `make` команди ті самі через `bun run`.
- «Підняти залежності» роблять самі тести: інтеграційні — `:memory:` або файл у `mkdtemp`, E2E — `mkdtemp`, вільний порт, процес `bun server/main.js` з `DB_PATH` і `PORT`, очікування `GET /version` до 20 с (spec, AC 5), зупинка процесу й видалення каталогу в `afterAll`. Docker і окремих скриптів підготовки немає.

### Мутації

`stryker.config.json`:

- `testRunner: "command"`, `commandRunner.command: "bun test ./tests/unit"`, `coverageAnalysis: "off"`;
- `mutate: ["server/core/**/*.js", "!server/core/errors.js"]`;
- мутатори — усі за замовчуванням; рядкові мутанти в текстах помилок класифікуються за правилом spec (контракт фіксує непорожній `error`, а не точний текст);
- `thresholds: { high: 90, low: 80, break: 80 }`: нижче 80 % команда завершується з кодом 1. Базовий прогін «До» може впасти нижче: це очікувано, звіт однаково зберігається, і саме він показує прогалини;
- `reporters: ["clear-text", "progress", "html", "json"]`, звіти в `reports/mutation/`, а `.stryker-tmp/` і `reports/` додаються в `.gitignore`;
- `incremental: false`: «До» і «Після» — повні прогони, щоб порівнювати однакові набори мутантів;
- `@stryker-mutator/core` — у `devDependencies` з точною версією (ADR 004).

Еквівалентні мутанти позначаються в коді коментарем `// Stryker disable next-line <мутатор>: еквівалентний — <причина>`, щоб не занижувати score. Прийнятні й реальні прогалини не вимикаються: перші лишаються у звіті з посиланням на spec, другі закриваються тестом.

Мутація вимірює unit-рівень `server/core/`. Якщо вижилого мутанта вбиває інтеграційний тест, він однаково класифікується як прогалина unit-рівня: `core/` — чисті функції, і їхню поведінку мають фіксувати unit-тести. У звіті це видно окремою позначкою «вбиває інтеграційний тест», щоб не плутати з поведінкою, якої не перевіряє ніщо.

### Покриття гілок

- Для `reports.js` — таблиця «гілка в коді → тест» у `docs/mutation-report.md`; кожен рядок посилається на випадок зі `specs/testing.md`, розд. 3.
- Для решти `server/core/` — вижилі мутанти умов (`ConditionalExpression`, `EqualityOperator`, `LogicalOperator`, `BlockStatement`) як список неперевірених гілок.
- `bun test --coverage` лишається для рядків і функцій; AC 2 (100 % рядків і функцій `reports.js`) перевіряється ним.

### CI

`bun run ci` запускає всі три рівні. Мутації в CI не входять: це хвилини на кожен push і потреба в окремому середовищі для Stryker. Відтворюваність дає `bun run mutation` (або `make mutation`) і звіт у `docs/mutation-report.md`.

### Перевірка перед `Accepted`

Рішення тримається на тому, що `command`-runner StrykerJS справді працює з `bun test` на Windows. Це ще не перевірено запуском. До зміни статусу на `Accepted` треба виконати й записати в «Context» результат:

1. `bun run mutation` на поточних unit-тестах завершується звітом (не помилкою запуску) на Windows.
2. Чи запускається сам Stryker через Bun (`bun x stryker run`), чи потрібен Node. Якщо потрібен Node — записати мінімальну версію як передумову лише для `mutation`.
3. Навмисно вставлений у `reports.js` баг (`<=` → `<` у `limitWarning`) дає вбитого мутанта: unit-тест рівно на ліміті його ловить. Це доводить, що активний мутант справді доходить до коду, який виконує `bun test` у пісочниці Stryker.
4. Час прогону на всьому обсязі — хвилини. Якщо ні, обсяг звужується до `reports.js` і ще одного модуля, а ADR оновлюється.

Якщо кроки 1–3 не проходять, переглядається варіант 2 з «Інструмент мутацій і runner» (сторонній runner) на Bun 1.4.4.

## Consequences

### Позитивні
- Однакові команди на Windows і в CI; `make test` і `make mutation` працюють там, де є `make`, без другої реалізації.
- Мутаційний прогін на unit-тестах — секунди на мутанта, без файлів і портів, тож «До» і «Після» можна повторювати скільки треба.
- Обсяг `server/core/` дає достатньо мутантів, щоб прогалини в «До» були справжніми.
- Межі рівнів перевіряє тест, а не домовленість.

### Негативні / компроміси
- Без per-test покриття кожен мутант запускає всі unit-тести; на більшому обсязі прогін ростиме лінійно.
- Score вимірює лише unit-рівень `core/`: сервіси, репозиторії й маршрути мутаціями не перевіряються. Їх захищають інтеграційні й E2E тести, ефективність яких мутаціями не виміряна.
- Покриття гілок поза `reports.js` показане опосередковано, через мутанти умов, а не відсотком.
- Нова dev-залежність і, можливо, Node як передумова лише для мутацій.
- Переїзд тестів у каталоги змінює шляхи в історії: `git log --follow` показує історію файлу, але посилання на рядки в старих тредах PR #3 ведуть на старі шляхи.
- `break: 80` на всьому `core/` може вимагати вимкнення еквівалентних мутантів коментарями в коді; кожен такий коментар має причину й рядок у звіті.

### Подальші дії
- Перевірка перед `Accepted` (кроки 1–4 вище).
- Переїзд тестів у каталоги й правила рівнів у тесті імпортів (AC 1).
- Скрипти `package.json`, `Makefile`, `stryker.config.json`, `.gitignore`.
- E2E-сценарій зі `specs/testing.md`, сценарій 3.
- Базовий прогін «До» → `docs/mutation-report.md`; нові тести й підсилення; прогін «Після».
- Оновити `specs/testing.md`: ВП-1…ВП-7 → посилання на цей ADR; `standards/checklist.md` і README — нові команди.
