# ADR 003: Визначення `today` за `Europe/Kyiv` та інжектований годинник

- **Status:** Accepted
- **Date:** 2026-11-05
- **Related spec:** `spec.md`, розд. 2, розд. 3 «Час», критерій 5

## Context

Від поточної дати (`today`) залежать три правила spec: відхилення майбутніх дат витрат, межі 30-денного вікна (`today - 29` … `today`) і заборона майбутнього `month` у місячному звіті. `today` має визначатися за `Europe/Kyiv`.

Проблеми:

- Найпростіший спосіб, `new Date().toISOString().slice(0, 10)`, повертає дату в UTC. Київ випереджає UTC на 2 години взимку і на 3 влітку, тож щодня з 22:00 (взимку) або 21:00 (влітку) до 24:00 UTC такий код вважає «сьогодні» вчорашню київську дату. Витрату за справжнє київське сьогодні буде відхилено як майбутню, а вікно зсунеться на день.
- Сервер може працювати в будь-якому часовому поясі (контейнер, хмара), тож локальний час машини теж не годиться.
- Віднімання 29 × 24 годин від миті ламається на переходах на літній/зимовий час (у 2026 році — 29 березня і 25 жовтня), коли доба триває 23 або 25 годин.
- Checklist вимагає тестів `T - 29`, `T - 30`, `T + 1` і межі доби в UTC. Якщо код читає системний час напряму, ці тести залежать від того, коли їх запускають, і не відтворюються.

## Decision Drivers

- **Коректність:** `today` збігається з київським календарем у будь-який момент доби й року.
- **Тестованість:** будь-який момент часу можна відтворити в тесті без зміни системного годинника.
- **Мінімум залежностей:** без сторонніх бібліотек дат.
- **Незалежність від середовища:** результат не залежить від `TZ` сервера.

## Considered Options

1. **UTC-дата через `toISOString()`:** просто, але дає неправильну дату 2–3 години щодоби.
2. **Фіксоване зміщення (`+02:00` або `+03:00`):** не враховує перехід на літній час; помилка двічі на рік або пів року поспіль.
3. **Бібліотека дат із часовими поясами:** коректно, але додає залежність заради однієї операції.
4. **`Intl.DateTimeFormat` з `timeZone: 'Europe/Kyiv'` + інжектована функція `now()` + арифметика календарних дат у UTC:** вбудовані засоби середовища, коректно враховує літній час, тести задають будь-яку мить.

## Decision

Обрано варіант 4.

- Застосунок створюється фабрикою з параметром `now` (за замовчуванням `() => new Date()`). Маршрути на кожен запит обчислюють `today = kyivToday(now())` і передають рядок `YYYY-MM-DD` у функції `server/core/`. Модулі `server/core/` не викликають `new Date()` без аргументів.
- `today` визначається через `Intl.DateTimeFormat` з явним часовим поясом:

  ```js
  const kyivFormat = new Intl.DateTimeFormat('en-CA', {
    timeZone: 'Europe/Kyiv',
    year: 'numeric',
    month: '2-digit',
    day: '2-digit',
  });

  export function kyivToday(now) {
    const p = Object.fromEntries(kyivFormat.formatToParts(now).map((x) => [x.type, x.value]));
    return `${p.year}-${p.month}-${p.day}`;
  }
  ```

- Межі вікна рахуються над календарними датами без годин: дата переводиться в UTC-північ, де переходів часу немає, і зсувається на потрібну кількість днів:

  ```js
  export function addDays(isoDate, days) {
    const [y, m, d] = isoDate.split('-').map(Number);
    return new Date(Date.UTC(y, m - 1, d + days)).toISOString().slice(0, 10);
  }
  // Вікно: [addDays(today, -29), today]
  ```

- Реальність дати перевіряється тим самим перетворенням: рядок, що відповідає `^\d{4}-\d{2}-\d{2}$`, валідний лише тоді, коли `addDays(s, 0) === s` (`2026-02-30` перетвориться на `2026-03-02` і не пройде).
- Дати у форматі `YYYY-MM-DD` порівнюються як рядки (лексикографічний порядок збігається з хронологічним); SQL-запити вікна використовують `spent_at BETWEEN ? AND ?`.
- Тести створюють застосунок із фіксованим `now`, наприклад `() => new Date('2026-07-15T21:30:00Z')` (у Києві вже `2026-07-16`).

## Consequences

### Позитивні
- `today` коректний цілодобово й протягом усього року, незалежно від `TZ` сервера.
- Переходи на літній/зимовий час не впливають на межі вікна.
- Усі граничні сценарії з checklist відтворюються детерміновано.
- Жодних нових залежностей.

### Негативні / компроміси
- Коректність залежить від даних часових поясів у середовищі виконання. Ідентифікатор `Europe/Kyiv` з'явився в базі IANA у 2022 році; у застарілому середовищі він може бути невідомим (там використовувався `Europe/Kiev`). Оскільки форматер створюється під час імпорту модуля, непідтримуваний пояс дасть `RangeError` уже на імпорті, без зрозумілого повідомлення.
- Розробники мають пам'ятати правило «жодного `new Date()` у `server/core/`»; це перевіряється код-рев'ю, а не інструментом.
- `today` обчислюється на кожен запит окремо, тож запит, що триває через київську північ, теоретично бачить стару дату. Для однокористувацького інструмента це прийнятно.

### Подальші дії
- Реалізувати `kyivToday`, `addDays` і перевірку дати в `server/core/`, фабрику застосунку з параметром `now`.
- Відкладено: зрозуміле повідомлення про непідтримуваний `Europe/Kyiv` (створювати форматер у функції ініціалізації або обгорнути в `try/catch`); записано у відкриті питання spec.
- Додати тести межі доби для літа й зими, переходу на літній час (вікно, що перетинає 29 березня 2026) і невалідних дат.
