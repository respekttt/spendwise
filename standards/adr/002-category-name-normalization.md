# ADR 002: Нормалізація назв категорій для регістронезалежної унікальності

- **Status:** Accepted
- **Date:** 2026-11-05
- **Related spec:** `spec.md`, розд. 3 «Назви», критерій 4

## Context

Spec вимагає, щоб назви категорій проходили `trim()` і порівнювалися без урахування регістру: `"інше"` і `" Інше "` мають вважатися дублікатами «Інше», а `"їжа"` — дублікатом `"Їжа"`.

Попередня версія схеми покладала це на `name TEXT UNIQUE COLLATE NOCASE`. Вбудована колація `NOCASE` у SQLite згортає регістр лише для латиниці A–Z. Для кирилиці `"Інше"` і `"інше"` вона вважає різними рядками, тож обмеження `UNIQUE` пропускає дублікати. Назви в проєкті переважно українські, тому правило фактично не працювало.

Додаткові факти:

- Одна й та сама літера може мати різне Unicode-представлення: `й` — як один символ (U+0439) або як `и` + комбінований знак (U+0438 U+0306); так само `ї`. Текст із різних джерел (копіювання, мобільні клавіатури) може приходити в будь-якій формі.
- Проєкт однокористувацький, категорій мало (десятки), тож продуктивність порівняння не критична.
- Бажано, щоб унікальність гарантувала БД, а не лише перевірка в коді.

## Decision Drivers

- **Коректність для кирилиці:** дублікати мають відхилятися незалежно від регістру й форми Unicode.
- **Гарантія на рівні БД:** обмеження має діяти навіть за помилки в коді чи прямого запису в SQLite.
- **Простота:** без розширень SQLite і нестандартних колацій.
- **Переносимість файлу БД:** файл має відкриватися будь-яким стандартним інструментом SQLite.

## Considered Options

1. **`UNIQUE COLLATE NOCASE` (попередній варіант):** нуль коду, але не працює для кирилиці — головна вимога не виконується.
2. **Перевірка лише в `server/core/`:** перед вставкою вибрати всі назви й порівняти в JS. Працює для кирилиці, але БД нічого не гарантує; пряма вставка чи помилка в іншому маршруті створить дублікат.
3. **Власна колація або розширення ICU для SQLite:** порівняння живе в БД, але колацію треба реєструвати на кожному з'єднанні, а сторонні інструменти (`sqlite3` CLI, переглядачі БД) без неї не зможуть працювати з індексом. Додає залежність від можливостей драйвера.
4. **Окрема колонка `name_normalized` з `UNIQUE`:** код обчислює нормалізовану форму, БД гарантує унікальність звичайним `UNIQUE`. Потрібно підтримувати узгодженість двох колонок.

## Decision

Обрано варіант 4.

- Таблиця `categories` отримує колонку `name_normalized TEXT NOT NULL UNIQUE`; `COLLATE NOCASE` з `name` прибирається.
- `name` зберігає назву для відображення: `name.trim().normalize('NFC')`.
- `name_normalized` обчислюється в `server/core/` однією функцією і лише нею:

  ```js
  export function normalizeCategoryName(name) {
    return name.trim().normalize('NFC').toLocaleLowerCase('uk');
  }
  ```

- Під час `POST` і `PUT /categories` сервер перевіряє, чи `trim()` дає непорожній рядок, і заздалегідь шукає збіг за `name_normalized` серед **інших** категорій (`WHERE name_normalized = ? AND id != ?`), щоб перейменування `"Їжа"` → `"їжа"` тієї ж категорії не відхилялося як дублікат і щоб повернути зрозуміле повідомлення з кодом `400`. Обмеження `UNIQUE` лишається останнім рубежем: порушення `SQLITE_CONSTRAINT_UNIQUE` також перетворюється на `400`.
- Системна категорія ідентифікується за `is_default = 1`, а не за назвою.
- Апострофи (`'`, `’`, `ʼ`), гомогліфи (латинська `I` і кирилична `І`) і повторні пробіли всередині назви не нормалізуються; це винесено у відкриті питання spec.

## Consequences

### Позитивні
- `"Їжа"`, `"їжа"`, `"  ЇЖА "` і варіанти з розкладеними `й`/`ї` дають однакове `name_normalized` і відхиляються як дублікати.
- Унікальність гарантує БД стандартним `UNIQUE`, без розширень і колацій; файл БД лишається переносним.
- Користувач бачить назву так, як ввів її (лише без крайових пробілів).

### Негативні / компроміси
- Дві колонки мають бути узгоджені: будь-який запис у `categories` в обхід `normalizeCategoryName` може їх розсинхронізувати.
- Пряма вставка в SQLite без `name_normalized` впаде через `NOT NULL`. Це навмисно, але ручні правки БД стають незручнішими.
- Правило нормалізації зафіксоване: його зміна (наприклад, уніфікація апострофів) потребує міграції наявних даних і нового ADR.

### Подальші дії
- Схема — `server/db/schema.sql` (без `COLLATE NOCASE`).
- Для наявних БД написати міграцію: додати колонку, заповнити її через `normalizeCategoryName`, перед створенням `UNIQUE`-індексу знайти й показати конфліктні назви.
- Додати тести: кириличний дублікат звичайної категорії, дублікати «Інше», назви з `"   "`, назва з розкладеним `й` (`"Мийка"` у формі NFD), перейменування `"Їжа"` → `"їжа"` тієї ж категорії (`200`).
