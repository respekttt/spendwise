# Шаблон архітектурного рішення — MADR (`adr-template.md`)

## Призначення та розміщення

ADR (*Architecture Decision Record*) зберігає причину важливого технічного рішення й розглянуті альтернативи. Створюйте запис у `standards/adr/NNN-short-title.md`, наприклад `standards/adr/001-money-representation.md`. Номер збільшується послідовно, файл не перейменовують після прийняття рішення без необхідності.

Секції **Status, Context, Decision, Considered Options, Decision Drivers, Consequences** обов'язкові. Решта метаданих — за потреби.

## Шаблон для копіювання

```markdown
# ADR NNN: <коротка назва рішення>

- **Status:** Proposed
- **Date:** YYYY-MM-DD
- **Related spec:** <шлях до spec або розділ>

## Context

<Яка проблема або суперечність виникла?>
<Які обмеження проєкту й факти потрібно врахувати?>

## Decision Drivers

- <Критерій 1: точність/безпека/простота/продуктивність/вартість>
- <Критерій 2>
- <Критерій 3>

## Considered Options

1. **<Варіант А>:** <переваги та недоліки>.
2. **<Варіант Б>:** <переваги та недоліки>.
3. **<Варіант В, якщо є>:** <переваги та недоліки>.

## Decision

<Обрано варіант ... . Що конкретно робимо, де саме і за яких умов?>
<Посилання на правила, формат даних, API чи тест, якщо потрібно.>

## Consequences

### Позитивні
- <Яку вигоду отримуємо?>

### Негативні / компроміси
- <Які ризики та обмеження приймаємо?>

### Подальші дії
- <Що потрібно реалізувати або перевірити?>
```

## Правила застосування

- **Status:** `Proposed` — обговорюється; `Accepted` — затверджено; `Deprecated` — більше не застосовується; `Superseded by ADR NNN` — замінено новим рішенням.
- В одному ADR фіксуйте **одну** значущу розвилку, а не кілька незалежних рішень.
- У `Decision` описуйте конкретний вибір; у `Context` — проблему, а не заздалегідь написане виправдання вибору.
- Не видаляйте прийняті ADR заднім числом: нове рішення оформлюйте новим ADR і позначайте старе як замінене.
- Після прийняття ADR відповідні `spec`, код і тести мають відповідати рішенню.
