# Definition of Done (DoD) — Expense Tracker

## Що означає «готово»

Завдання вважається **Done**, коли виконано всі релевантні пункти нижче, пройдено необхідні перевірки та зафіксовано результат. Якщо пункт не стосується завдання, позначайте його `N/A` з короткою причиною; не видавайте неперевірену функціональність за готову.

## 1. Реалізація

- [ ] Реалізовано всі критерії прийняття відповідного spec; поведінка не виходить за погоджені `In Scope`.
- [ ] Збережено поділ відповідальності: `server/routes/` — HTTP, `server/core/` — правила, `server/db/` — SQLite, `public/` — UI.
- [ ] Сервер перевіряє вхідні дані, зокрема типи (`amount` — число, а не рядок); фронтендна валідація не є єдиним захистом.
- [ ] Коректно працюють коди `200/201`, `400` і `404` у відповідних сценаріях; помилки повертаються у форматі з [контракту API](../specs/api-contract.md).
- [ ] Зміни БД не порушують зовнішні ключі; `PRAGMA foreign_keys = ON` виконується для **кожного** з'єднання; багатокрокові операції виконуються транзакційно.
- [ ] `server/core/` не читає системний час напряму: `today` обчислюється з інжектованого годинника (ADR 003).
- [ ] UI показує результат дії, помилки та `warning`, не губить уведені дані без потреби.

## 2. Правила Expense Tracker — коли завдання їх зачіпає

- [ ] Сума й ліміт спочатку округлюються `Math.round(value * 100) / 100`, потім перевіряються на `> 0`; звітні суми подаються з точністю до 2 знаків.
- [ ] `0.10 + 0.20` коректно відображається як `0.30`; за ліміту `0.30` ці витрати не дають `warning`, бо сума за 30 днів округлюється перед порівнянням; `0.004` після округлення відхиляється кодом `400`.
- [ ] Дата має формат `YYYY-MM-DD`, є реальною календарною датою і не пізніша за сьогодні за `Europe/Kyiv`; параметр `month` має формат `YYYY-MM`, місяць `01`–`12` і не пізніший за поточний, інакше `400`.
- [ ] 30-денний період включає `today - 29` і `today`, але не включає `today - 30`.
- [ ] «Інше» існує після ініціалізації в одному екземплярі; її заборонено перейменовувати, видаляти й встановлювати їй ліміт; назви категорій перевіряються через `trim()` і без урахування регістру, зокрема для кирилиці (ADR 002); дублікати й будь-які зміни «Інше» повертають `400`.
- [ ] Під час видалення звичайної категорії витрати переносяться в «Інше» в одній транзакції; у разі збою зміни відкочуються; загальна сума витрат не змінюється.
- [ ] Перевищення ліміту **не блокує** збереження: зміна успішна й API повертає `warning` зі структурою з контракту API і сумою перевищення. Під час зміни категорії витрати ліміт перевіряється для **нової** категорії.
- [ ] Частки у звітах округлюються до 2 знаків; сума часток відхиляється від 100% не більше ніж на `0.005 × N`, де N — кількість категорій у звіті; за періоду без витрат звіт повертає `total = 0` і порожній список без ділення на нуль.
- [ ] Місячний звіт містить лише суму та частки за обраний місяць; 30-денний звіт додатково містить стани лімітів.
- [ ] `GET /version` повертає короткий Git SHA поточного коміту як `text/plain` (для завдань, що зачіпають реліз/версію).

## 3. Якість і перевірки

- [ ] `bun run check` (Biome) завершився без помилок у підтримуваних файлах.
- [ ] `bun test` завершився успішно; нова або виправлена поведінка має відповідні тести, включно з негативними й граничними сценаріями.
- [ ] Тести, що залежать від дати, використовують фіксований годинник, а не поточний час машини.
- [ ] Для змін API/БД виконано інтеграційну перевірку з ізольованою тестовою SQLite БД.
- [ ] Для змін UI вручну перевірено основний сценарій у браузері та відображення помилок і попереджень.
- [ ] `bun run build` завершився без помилок.
- [ ] **CI пройшов** (`bun run ci`) для останнього коміту гілки. Локальний `pre-commit` hook не замінює CI.
- [ ] Git `pre-commit` hook, якщо налаштований, проходить без пропуску перевірок.
- [ ] Немає випадково закомічених SQLite-даних користувача, секретів, тимчасових файлів чи налагоджувальних повідомлень; `.gitignore` містить шаблони з checklist.

## 4. Документація і передача

- [ ] Актуалізовано spec, `specs/api-contract.md` і `server/db/schema.sql`, якщо змінилась поведінка; за архітектурного компромісу додано/оновлено відповідний ADR.
- [ ] Інструкції запуску і тестування актуальні; важливі обмеження й відомі проблеми документовано.
- [ ] Зміни переглянуто, вони придатні до злиття; у PR/коміті вказано номери підтверджених критеріїв прийняття spec.

## Правило завершення

**Done = реалізація + докази перевірки (зокрема зелений CI) + актуальна документація.** Якщо тест упав, перевірка не запускалась, CI не пройшов або критерій прийняття не виконано, статус залишається `In Progress` / `Blocked`, а не `Done`.
