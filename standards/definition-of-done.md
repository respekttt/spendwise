# Definition of Done (DoD) — Expense Tracker

## Що означає «готово»

Завдання вважається **Done**, коли виконано всі релевантні пункти нижче, пройдено необхідні перевірки та зафіксовано результат. Якщо пункт не стосується завдання, позначайте його `N/A` з короткою причиною; не видавайте неперевірену функціональність за готову.

## 1. Реалізація

- [ ] Реалізовано всі критерії прийняття відповідного spec; поведінка не виходить за погоджені `In Scope`.
- [ ] Збережено поділ відповідальності: `server/routes/` — HTTP, `server/core/` — правила, `server/db/` — SQLite, `public/` — UI.
- [ ] Сервер перевіряє вхідні дані; фронтендна валідація не є єдиним захистом.
- [ ] Коректно працюють коди `200/201`, `400` і `404` у відповідних сценаріях.
- [ ] Зміни БД не порушують зовнішні ключі; `PRAGMA foreign_keys = ON` активовано; багатокрокові операції виконуються транзакційно.
- [ ] UI показує результат дії, помилки та `warning`, не губить уведені дані без потреби.

## 2. Правила Expense Tracker — коли завдання їх зачіпає

- [ ] Сума й ліміт спочатку округлюються `Math.round(value * 100) / 100`, потім перевіряються на `> 0`; звітні суми подаються з точністю до 2 знаків.
- [ ] `0.10 + 0.20` коректно відображається як `0.30`; `0.004` після округлення відхиляється кодом `400`.
- [ ] Дата має формат `YYYY-MM-DD`, є реальною календарною датою і не пізніша за сьогодні за `Europe/Kyiv`.
- [ ] 30-денний період включає `today - 29` і `today`, але не включає `today - 30`.
- [ ] «Інше» існує після ініціалізації; її заборонено перейменовувати, видаляти й встановлювати їй ліміт; назви категорій перевіряються через `trim()` і без урахування регістру.
- [ ] Під час видалення звичайної категорії витрати переносяться в «Інше» в одній транзакції; загальна сума витрат не змінюється.
- [ ] Перевищення ліміту **не блокує** збереження: зміна успішна й API повертає `warning` із сумою перевищення.
- [ ] Місячний звіт містить лише суму та частки за обраний місяць; 30-денний звіт додатково містить стани лімітів.
- [ ] `GET /version` повертає короткий Git SHA поточного коміту (для завдань, що зачіпають реліз/версію).

## 3. Якість і перевірки

- [ ] `bunx biome check .` завершився без помилок у підтримуваних файлах.
- [ ] `bun test` завершився успішно; нова або виправлена поведінка має відповідні тести, включно з негативними й граничними сценаріями.
- [ ] Для змін API/БД виконано інтеграційну перевірку з ізольованою тестовою SQLite БД.
- [ ] Для змін UI вручну перевірено основний сценарій у браузері та відображення помилок і попереджень.
- [ ] Git `pre-commit` hook, якщо налаштований, проходить без пропуску перевірок.
- [ ] Немає випадково закомічених SQLite-даних користувача, секретів, тимчасових файлів чи налагоджувальних повідомлень.

## 4. Документація і передача

- [ ] Актуалізовано spec, якщо змінилась поведінка; за архітектурного компромісу додано/оновлено відповідний ADR.
- [ ] Інструкції запуску і тестування актуальні; важливі обмеження й відомі проблеми документовано.
- [ ] Зміни переглянуто, вони придатні до злиття; у PR/коміті вказано, які критерії прийняття підтверджено.

## Правило завершення

**Done = реалізація + докази перевірки + актуальна документація.** Якщо тест упав, перевірка не запускалась або критерій прийняття не виконано, статус залишається `In Progress` / `Blocked`, а не `Done`.
