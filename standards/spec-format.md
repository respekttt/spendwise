# Стандарт оформлення специфікацій (`spec-format.md`)

## Призначення

Кожна функціональна специфікація Expense Tracker — це Markdown-документ, який описує **межі**, **архітектуру**, **дані та правила**, **сценарії змін** і **перевірювані критерії прийняття**. Структуру взято з наявної специфікації «Трекер витрат (Expense Tracker)».

Рекомендоване розташування: `specs/<назва-функції>.md`. **Обсяг spec — не більше однієї сторінки.** Деталі контракту API і схеми БД виносяться в окремі файли (`specs/api-contract.md`, `server/db/schema.sql`), spec посилається на них; вимоги цього стандарту до маршрутів, форматів і обмежень БД виконуються в цих файлах. Для загальної специфікації проєкту допустимий файл `spec.md` у корені. Назви файлів — у `kebab-case`.

## Обов'язкові розділи та порядок

| № | Розділ | Що обов'язково описати |
|---|---|---|
| 1 | **Межі проєкту / функції** | `In Scope` — що реалізуємо; `Out of Scope` — чого свідомо не робимо. |
| 2 | **Архітектура та компоненти** | Задіяні шари, їхня відповідальність, зв'язки, стек; перелік маршрутів із методами та HTTP-кодами (у spec або в контракті API за посиланням); за потреби — схема потоків даних. |
| 3 | **Дані та бізнес-правила** | Поля й типи, обмеження БД, формати, валідація, округлення, часовий пояс, інваріанти; формат запитів і відповідей та SQL-схема — у spec або в окремих файлах за посиланням. |
| 4 | **Ключові сценарії оновлення даних** | Що запускає дію, як дані перевіряються і змінюються, транзакції, попередження, результат для користувача/API. |
| 5 | **Критерії прийняття** | Нумеровані спостережувані результати, зокрема позитивні, негативні та граничні випадки. |
| 6 | **Відкриті питання** *(необов'язковий)* | Питання, які ще не узгоджено. Розділ іде останнім, щоб не порушувати порядок 1–5; якщо питань немає, його не додають. |

## Вимоги до змісту

- Пишіть українською; технічні ідентифікатори (`amount`, `category_id`, `warning`, назви маршрутів) залишайте без перекладу.
- Вказуйте точні формати (`YYYY-MM-DD`, `YYYY-MM`), валюту (UAH), часовий пояс (`Europe/Kyiv`) і статуси HTTP там, де це впливає на результат.
- Не залишайте нечітких формулювань на кшталт «правильно обробляється». Вказуйте **вхідну умову → дію → очікуваний результат**.
- Описуйте структуру кожної нестандартної відповіді: поля попереджень (`warning`), тіла помилок, звітів, а також тип вмісту для не-JSON відповідей (`text/plain`). Формулювання «повертає попередження» без структури недостатнє.
- Описуйте граничні випадки порожніх даних: період без витрат, категорію без витрат, ділення на нуль у частках.
- Для кожного обмеження вказуйте, де воно забезпечується: у БД (`CHECK`, `UNIQUE`, `NOT NULL`, індекс) чи в `server/core/`. Не покладайтеся на можливості SQLite, які не працюють для кирилиці (наприклад, `COLLATE NOCASE`).
- Розділи 4 і 5 оформлюйте нумерованими списками, щоб на пункти можна було посилатися з тестів, DoD і PR.
- Розмежовуйте правила, які вже узгоджено, і питання, які ще потребують рішення: останні виносьте в розділ 6. Архітектурні компроміси оформлюйте окремим ADR у `standards/adr/`.
- Діаграми даних додавайте у форматі Mermaid або текстовою схемою; вони мають узгоджуватися з правилами БД. Якщо є SQL-схема (`server/db/schema.sql`), саме вона є джерелом істини, а діаграма в spec — оглядом.
- Нові вимоги не повинні суперечити загальній специфікації; за потреби спочатку узгодьте зміну й оновіть відповідний ADR.

## Приклади конкретності для Expense Tracker

- **Округлення:** суми `0.10` та `0.20` грн дають суму звіту `0.30` грн, а за ліміту `0.30` не дають `warning`; після округлення `0.004` → `0`, тож API повертає `400`.
- **Календарне вікно:** останні 30 днів — від `today - 29` до `today` включно в `Europe/Kyiv`, а не 30 × 24 годин від поточної миті.
- **Межа доби:** о `2026-07-15T21:30:00Z` у Києві вже `2026-07-16`.
- **Системна категорія:** «Інше» не можна видалити, перейменувати або забезпечити лімітом; дублікати без урахування регістру заборонені, зокрема кириличні (`"Їжа"` / `"їжа"`).
- **Коди API:** невалідні дані в тілі або query-параметрах запиту (`?month=2026-13`) — `400`; неіснуючий `:id` у URL — `404`.
- **Порожні дані:** звіт за період без витрат — `total = 0`, `categories = []`, код `200`.
