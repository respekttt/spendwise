# ADR 001: Представлення грошових сум

- **Status:** Accepted
- **Date:** 2026-11-05
- **Related spec:** `spec.md`, розд. 3 «Гроші», критерії 1, 2, 6

## Context

Expense Tracker зберігає суми витрат (`amount`) і ліміти категорій (`limit_amount`) у гривнях з точністю до копійки, рахує суми за періоди, частки у звітах і порівнює витрачене з лімітом.

Числа в JavaScript і тип `REAL` у SQLite — це двійкові числа з плаваючою комою (IEEE 754, double). Більшість десяткових дробів у них не представляються точно:

- `0.1 + 0.2` дає `0.30000000000000004`, тож без округлення сума витрат `0.10` і `0.20` строго більша за ліміт `0.30` і дає хибний `warning`.
- `1.005 * 100` дає `100.49999999999999`, тому `Math.round(1.005 * 100) / 100` повертає `1`, а не `1.01`. Водночас `0.005` округлюється до `0.01`, а `10.005` — до `10.01`: половинні значення на третьому знаку округлюються непослідовно.
- Похибка накопичується: сума 100 000 витрат по `0.10` дорівнює `10000.000000018848`.

Обмеження проєкту:

- Одна валюта (UAH), один користувач, обсяги — тисячі або десятки тисяч записів.
- API приймає суми як JSON-числа, тобто значення вже приходить у вигляді double; точний десятковий рядок на сервер не потрапляє.
- Стек без додаткових залежностей: Bun, Fastify, bun:sqlite, Vanilla JS.
- Користувач вводить суми з UI, де достатньо двох знаків після коми.

## Decision Drivers

- **Коректність для користувача:** звіти й перевірка лімітів мають давати очікувані результати для сум із двома знаками (`0.10 + 0.20 = 0.30`).
- **Простота:** мінімум перетворень між API, кодом і БД; читабельні значення в БД і JSON.
- **Відсутність залежностей:** без бібліотек десяткової арифметики.
- **Передбачуваність:** правило округлення має бути одним і однаково застосовуватися всюди.

## Considered Options

1. **`REAL` + округлення до 2 знаків на вході й виході:** суми зберігаються як `REAL`; кожне вхідне значення та кожен підсумок округлюється `Math.round(val * 100) / 100`. Просто, читабельно в БД і JSON, без перетворень. Недоліки: похибка між округленнями зберігається, межа `1.005` округлюється вниз, а коректність залежить від того, чи не забули округлити підсумок перед порівнянням.
2. **`INTEGER` у копійках:** БД і `server/core/` працюють із цілими копійками, API конвертує на межі. Суми й порівняння точні, накопичення похибки немає. Недоліки: перетворення при кожному вводі й виводі, ризик помилки «у 100 разів», менш читабельна БД; межу `1.005` на вході це не прибирає, бо JSON-число вже є double.
3. **Десятковий рядок + бібліотека (`decimal.js` тощо) або API із сумою-рядком:** найточніше, зокрема `"1.005"` можна округлити правильно. Недоліки: нова залежність, рядкові суми в API та БД, агрегування `SUM()` у SQLite для рядків не працює без перетворень.

## Decision

Обрано варіант 1: `REAL` з обов'язковим округленням у визначених точках.

- Одна функція округлення в `server/core/`, яку використовують усі модулі:

  ```js
  export const roundMoney = (value) => Math.round(value * 100) / 100;
  ```

- **Вхід:** `amount` і `limit_amount` спершу округлюються, потім перевіряються `Number.isFinite` і `> 0` (тому `0.004` стає `0`, а `1e308` — `Infinity`, і обидва дають `400`); зберігаються вже округленими.
- **Підсумки:** результат `SUM(amount)` округлюється перед будь-яким використанням: у звітах, у порівнянні з лімітом, в обчисленні `remaining` і `exceeded_by`. `warning` виникає лише тоді, коли `roundMoney(spent) > limit_amount`.
- **Частки:** `share = Math.round(category_total / total * 10000) / 100`; кожна частка має похибку до ±0.005, тож сума часток відхиляється від 100% не більше ніж на `0.005 × N`, де N — кількість категорій у звіті (за шести рівних категорій — `100.02%`).
- **Відображення:** API повертає суми як JSON-числа; UI форматує їх з двома знаками (`toFixed(2)`).
- **Межа `1.005`:** приймається як відомий компроміс. Значення з третім знаком після коми, що закінчується на `5`, можуть округлитися як вгору (`0.005` → `0.01`), так і вниз (`1.005` → `1`). Щоб користувач не вводив такі значення, поле суми в UI має `step="0.01"`.

## Consequences

### Позитивні
- `0.10 + 0.20` дає `0.30` у звітах і не викликає хибного `warning` за ліміту `0.30`.
- Схема БД, JSON і код лишаються простими; суми читабельні в БД без перетворень.
- `SUM()` і порівняння виконуються засобами SQLite та JS без додаткових залежностей.
- Для обсягів проєкту накопичена похибка (порядку `1e-8` на 100 000 записів) повністю прибирається округленням до копійок.

### Негативні / компроміси
- Значення з третім знаком `5` округлюються непослідовно (`1.005` → `1`, `10.005` → `10.01`). Для API-клієнтів, що надсилають три знаки, результат може відрізнятися від шкільного округлення.
- Коректність тримається на дисципліні: будь-яке нове місце, де підсумок порівнюється чи показується без `roundMoney`, поверне проблему `0.30000000000000004`.
- Для мультивалютності, банківської точності або значно більших обсягів цього рішення буде недостатньо; тоді його замінить новий ADR (ймовірно, варіант 2), з міграцією даних.

### Подальші дії
- Реалізувати `roundMoney` в `server/core/` і використовувати її в усіх розрахунках, а не `toFixed` чи власні варіанти округлення.
- Додати `step="0.01"` до полів суми й ліміту в `public/`.
- Відкладено: `step` не діє, якщо форма відправляється через `fetch` без `form.checkValidity()`; записано у відкриті питання spec.
- Додати тести: `0.10 + 0.20 = 0.30`; ліміт `0.30` без `warning`; `0.004` і `1e308` → `400`; `0.005` → збережено `0.01`; `1.005` → збережено `1` (фіксує відомий компроміс); суми рівно на ліміті без `warning`.
